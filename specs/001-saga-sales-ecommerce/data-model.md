# Data Model: Saga-Sales E-Commerce Platform

*Phase 1 output of `/speckit-plan`*

Implements the entities of [`spec.md`](./spec.md) under the persistence rules of
[`research.md`](./research.md) R1, R2, R5 and R6.

---

## 1. Databases

One PostgreSQL 16 instance, one database per service, no cross-database query.

| Service | Database | Owner of |
|---|---|---|
| Identity | `saga_identity` | tenants, users |
| Catalog | `saga_catalog` | products, prices, categories, stock |
| Sales | `saga_sales` | orders, order lines |
| Payment | `saga_payment` | payments, order references |
| Customer | `saga_customer` | customers, addresses |
| Analytics | `saga_analytics` | daily aggregates |
| Notification | `saga_notification` | notification logs, templates |

Every database carries:

```sql
create table schema_version (
  version     integer primary key,
  script      text        not null,
  applied_at  timestamptz not null default now()
);
```

---

## 2. Conventions

1. **Tenant first**: every procedure that touches business data receives `p_tenant_id uuid` as its
   first parameter and filters on it. There is no procedure that reads across tenants.
2. **Identifiers**: `uuid` generated by the application (`gen_random_uuid()` only for seed data).
3. **Money**: `numeric(18,2)`. Never `float`. Currency is fixed to `USD` (D6).
4. **Timestamps**: `timestamptz`, always UTC in storage.
5. **Soft delete**: a state column, never `DELETE`, for products, customers and orders.
6. **Enums**: stored as `smallint` with a `check` constraint listing the allowed codes, so the
   database rejects an invalid state even if a handler is wrong.
7. **Errors**: procedures signal domain failures with `raise exception` using a stable code in the
   message prefix (`INSUFFICIENT_STOCK`, `INVALID_TRANSITION`, `NOT_FOUND`, `CONFLICT`), which the
   API maps to a status code.

### State machine

```
pending ──► confirmed ──► processing ──► shipped ──► delivered ──► refunded
   │            │             │
   └────────────┴─────────────┴──────► cancelled          (final)
```

Enforced by `sp_order_change_status`, which raises `INVALID_TRANSITION` for anything else.

### Procedures

| Procedure | Signature | Rule |
|---|---|---|
| `sp_order_create` | (p_tenant_id, customer_id, shipping_address, notes, created_by, lines jsonb) → order | one transaction; writes lines with snapshot |
| `sp_order_get` | (p_tenant_id, order_id) → order + lines | |
| `sp_order_list` | (p_tenant_id, page, size, status) → rows + total_count | |
| `sp_order_change_status` | (p_tenant_id, order_id, new_status) | validates the transition |
| `sp_order_register_payment` | (p_tenant_id, order_id, amount) | adds to `paid_amount`, confirms a pending order |

## 10. Validation rules (from the spec)

| Rule | Where enforced |
|---|---|
| Product name ≥ 2 chars, price > 0, stock ≥ 0 | handler validator **and** `check` constraint |
| Category name unique per tenant | unique index |
| Customer email unique per tenant | unique index |
| Stock never negative | `check (stock_quantity >= 0)` |
| Refund never exceeds refundable | `check (refunded_amount <= amount)` + procedure guard |
| Order status transitions | `sp_order_change_status` |
| One live payment per order | `sp_payment_create` |
| Tenant always present | first parameter of every procedure |
| Shipping address required | `orders.shipping_address not null` |

## 11. Reserved for the separate invoicing project (E-10)

Present in the schema, never written by this platform today:
`orders.fiscal_status`, `orders.fiscal_document_number`, `orders.tax_amount`,
`order_lines.tax_rate`, `products.fiscal_note`.

This is what makes D3 safe: the invoicing project can be built later without migrating historical
orders.
